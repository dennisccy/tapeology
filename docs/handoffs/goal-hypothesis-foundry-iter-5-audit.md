## 1. Executive Verdict

**Verdict:** PASS_WITH_GAPS

The phase goal was achieved: the era's one real Foundry epoch exists, was generated by the real
production chain over 11 real source records with a genuinely independent fresh-context audit that
caught and fixed two defects pre-commit, is frozen in a single Git commit (`dff64eaa`, ancestor of

What the pipeline did **not** catch is that the artifact this whole era rests on had no automated
guard of any kind, and that two of its integrity claims are not true as written: the §1.4 citation
lint never reaches the files it cites, and `freeze_commit` does not contain the science bytes the
freeze-set pins. I fixed the coverage hole and the false claims; two IMPORTANT gaps remain that
block J-07 (the first-read lock), not this iteration's deliverable.

## 2. Findings

### Backend Findings

**B1 — IMPORTANT (gap, not fixed): the committed freeze-set pins absolute, machine-local paths, so
the §8.5 first-read lock can pass against the wrong files.**

`docs/hypothesis-foundry/freeze-set.json` keys all 55 entries by absolute path
(`/home/dennis-chan/Git/tapeology/apps/backend/app/research/…`), because
`generate_freeze_set` records `str(research_dir / name)` (`apps/backend/app/research/
foundry_freeze.py:198`) and the CLI passes the absolute `BACKEND_DIR`
(`apps/backend/scripts/generate_hypothesis_foundry_real_epoch.py:914-915`).
`verify_freeze_set_unchanged` (`foundry_freeze.py:268-296`) resolves each key literally via
`Path(path_str)`.

The reviewer filed this as a MINOR portability note. It is worse than that in one specific,
realistic scenario this project actually uses: in a **second git worktree on this machine**, the
lock recomputes hashes for `/home/dennis-chan/Git/tapeology/...` — the *original* tree — while the
runner executes the worktree's copy. The lock would report "unchanged" against files the process is
not running. From any other checkout it fails closed (`FreezeIntegrityHalt`, `path.is_file()` false),
which is safe but makes the freeze unverifiable anywhere else. §8.4 names the recomputed freeze-set
hashes "the enforceable primitive" and the file "an enumerated checked-in path+sha256 manifest", so
this defeats the mechanism's stated purpose off this one directory.

*Not fixed, deliberately.* The repair (store repo-relative keys; resolve them against the repo root
in `verify_freeze_set_unchanged`, passing absolute keys through for the hermetic temp-dir fixtures)
changes production freeze semantics **and** requires rewriting the already-committed
`freeze-set.json` plus `freeze-record.json`'s `freeze_set_hash`. `freeze_set_hash` is not part of
`generation_inputs` (`generate_hypothesis_foundry_real_epoch.py:901-907`), so `epoch_id` and
`manifest_hash` would survive that — it is technically safe — but amending a post-barrier frozen
artifact of an era that permits no second epoch is an owner ruling under §7.3/§8.3, not an auditor's
call. Recommended before J-07 runs; a portable equivalent drift-guard now exists in
`test_freeze_set_entries_still_match_the_science_files_in_this_checkout`.

**B2 — IMPORTANT (partially fixed): `freeze_commit` does not contain the science bytes the
freeze-set pins, so the "Git-visible" freeze is not Git-recoverable.**

Verified directly: of the 55 freeze-set entries, `apps/backend/app/research/foundry_compiler.py`'s
pinned sha256 matches the working tree but matches **neither** `55c42ee3` (the recorded
`freeze_commit`) **nor** `dff64eaa` (`HEAD`) — the iteration's own 7→8 fixture change to that file is
still uncommitted. The generation script asserted the opposite in its header docstring: *"it already
reflects the exact frozen science-file state the freeze-set hashes were computed from (this script
never modifies any science file)"*. The script indeed modifies nothing, but it hashes the **working
tree**, so any freeze-set path carrying an uncommitted change is pinned at a byte state present in no
commit. §8.4's literal requirement ("no freeze-set path has an uncommitted byte change relative to
the recorded hash set") still holds — the disk matches the hashes — but a `git checkout --` on that
one path would destroy a state no second epoch may recreate (§8.1).

*Fixed in part:* the false claim is corrected in place, with the ordering rule the generator should
have carried (commit freeze-set paths before or immediately after generation). The durable remedy is
committing this iteration's science-file changes, which the pipeline's finalize step performs.

**B3 — IMPORTANT (fixed): §1.4's mechanical citation lint never reaches the cited ratified source,
and the registry's "copied VERBATIM" claim is false.**

`lint_quoted_spans` (`apps/backend/app/research/foundry_source_registry.py:228-243`) verifies a span
is a substring of **its own record's** `source_excerpt`, and `source_hash` is
`sha256(source_excerpt)` (same file, line 221) — both sides authored by the same developer in the
same file. Nothing in the production path ties the frozen registry to the files it cites, though
§1.4 states: *"Mechanical registry lint verifies that every quoted span is an exact substring of the
cited ratified source at the recorded location."*

I ran that missing check by hand over all 11 committed records. **Content is sound** — every span
traces to real ratified text — but **0 of 11 excerpts are byte-exact substrings** of their
`source_path`. Divergences are markdown emphasis/backtick/blockquote+list-marker removal, Python
comment-hash removal, line rejoining, and Unicode→ASCII (`≥`→`>=`, `—`→`--`, `·`→`*`); two spans are
genuine notational **transliterations** (`Σ_{i≤t, side_i ≠ unknown} sign(side_i)·size_i` → `"sum over
i<=t, side_i != unknown of sign(side_i)*size_i"`, Card 9.1; `k ∈ {5, 10, 20}` → `"k in {5, 10, 20}"`,
Card 9.6); and several excerpts concatenate disjoint spans of one file behind a synthetic ` || `
separator (the two pilot-study records join a comment block to `PILOT_STUDY_STATUS` dict values).
The generator's own header comment claimed *"copied VERBATIM (whitespace-normalized from the wrapped
original only)"* — untrue as stated.

*Fixed:* the claim is corrected to describe the real transformation, and
`tests/test_foundry_real_epoch_artifacts.py::test_every_quoted_span_is_traceable_to_the_ratified_source_file_it_cites`
now performs the cross-file check under an explicit, documented normalization, with the two
transliterations listed as named exceptions each anchored to an ASCII-invariant fragment that must
still be present in the cited file. Any *other* divergence — source drift, or a citation that was
never real — now fails the suite.

**B4 — IMPORTANT (fixed): the frozen epoch had zero automated coverage; TC-1..TC-6, TC-9 and TC-10
were never implemented.**

The spec's TESTING REQUIREMENTS and `runs/goal-hypothesis-foundry-iter-5/plan.md` both call for
unit/integration coverage of the real registry compilation, generation, and replay-verification.
`grep -rln "source-registry.json\|build_real_source_records" apps/backend/tests/` returned only
`test_foundry_route.py`, whose new tests cover the route's degrade path — not the artifacts. Nothing
in the 3,879-test suite would have noticed a hand-edited disposition, a dropped `audit_note`, a
non-zero census, or the five files leaving `HEAD` — on an artifact that can never be regenerated.

*Fixed:* added `apps/backend/tests/test_foundry_real_epoch_artifacts.py` (14 read-only tests, no
generation, no writes) covering TC-1 (11 records, closed §7.1 vocabulary, non-empty
`audit_note`/`source_hash`, plus recompilation through the real `compile_sources` reproducing the
committed `source_registry_hash` and every disposition), TC-2/TC-3/TC-4/TC-5, TC-6 (census 0 on both
the artifact and the served view, plus an assertion that no outcome-shaped key appears anywhere in
the manifest), TC-9 (all five files added in one commit that is an ancestor of `HEAD`; freeze-commit
ancestry; no exhaust-runner call site outside the hermetic summary), TC-10 (replay returns the same
`epoch_id`, drift raises `ManifestDriftRefused`), the freeze-set drift guard from B1, and B3's
provenance check.

**B5 — IMPORTANT (gap, owner decision required): a first real `epoch_id` was minted and discarded,
and the "at most one real epoch" rule is enforced only by a file's presence.**

`reports/hypothesis-foundry/source-registry-audit.md:9-40` records it plainly: the audited registry
had `source_registry_hash ded18b8b896b…`, the post-audit fix to
`card-9.6-shuffled-side-persistence`'s `direction_derivation` changed it to `ed40dbc25e8f…`, and
*"`source_registry_hash` and therefore `epoch_id` changed on regeneration."* So two real `epoch_id`s
have existed, against §8.1's *"This era creates at most one real `epoch_id`"*.

The mechanism that should have refused this was bypassed rather than overruled:
`_load_existing_manifest_store` (`generate_hypothesis_foundry_real_epoch.py:858-875`) returns `{}`
when `epoch-manifest.json` is absent, and `generate_or_verify_manifest` then mints a fresh epoch with
no refusal at all. `ManifestDriftRefused` only fires when the tracked file is present — deleting it
is a silent bypass.

Strong mitigation, and it is why this is not a CRITICAL: no candidate outcome was ever read (no
Foundry ledger exists; `apps/backend/.data/foundry/` holds only the era-open baseline), nothing was
committed under the first hash, the change corrected a field an *independent* audit proved
unsupported rather than anything outcome-shaped, §7.3 explicitly permits repair before any real
outcome read, and the whole sequence is disclosed in the committed audit report. That is the honest
handling. But the era's history now contains a discarded real epoch, and the guarantee is mechanical
in name only. **This needs owner ratification before J-07**, not a code fix — I did not invent a new
uniqueness guard, since designing §8.1's enforcement is out of this phase's scope.

*I was unsure between IMPORTANT and GAP here and chose the higher, per the rubric.*

## 3. Domain Assessment

The core scientific logic is sound, and in two places better than the spec that asked for it.

**The dispositions are right.** I read every one of the 11 records against its cited text. Card 9.3
"adds confirm/veto information" states no direction → `BLOCKED_DIRECTION`, not a threshold block, and
`natural_semantic_boundary` is correctly retained for the signed-zero boundary. Card 9.4's "session
extremes"/"genuine breaks" are exactly §2.2's undefined-magnitude class → `BLOCKED_SPEC_GAP`. Card
9.6's two clauses genuinely differ in statistical form and correctly receive separate records per
§1.3. Card 9.7 is a textbook §1.3 supersession into existing feature vocabulary →
`ALIASED_VARIANT_VOCABULARY`. The three exclusion records cite historical facts (a prior kill, an
unmet prerequisite, a closed gate) as *provenance* — never as likelihood arguments, which is the
anti-goal that matters most here. **Zero compiled candidates is the correct outcome**, and the
project's willingness to ship an empty epoch rather than manufacture one is the single most valuable
thing in this iteration.

**The fresh-context audit was real, not ceremonial.** It found a defect the developer's own tests
never would have (the JSON serializer reused `_canonical_source_record`, the *hash-canonicalization
projection*, silently dropping `audit_note` from every committed record) and traced it to root cause;
and it rejected an unsupported `direction_derivation: "long"` on Card 9.6 that had been copied from
the source's adjective for run *length*. Both were fixed before the barrier. That is the §1.4
contract working as designed.

**The anti-goal closure is genuine.** `_fragile_killed_anchors_natural()` reaches `killed_fragile`
through the real, unmodified `scout._two_sided_p` — three seeded sessions with a dominant
strongly-positive session and two smaller negative ones, so leave-one-session-out flips the sign
honestly. The dominant session's anchor count (8000 vs 2000) is deliberately oversized so the
"biggest candidate-count session" is deterministic rather than a coin flip on the per-anchor draw — a
real failure mode the developer found and documented while tuning. Verified live: the served
`outcome_types_present` contains `fragility_killed` with no monkeypatch anywhere in the serving path,
and the grep guard is now a test, not a shell command in a handoff.

**The route read path is exactly right.** `read_epoch_manifest_view` reads the literal repo-relative
tracked paths and never `resolve_foundry_dir()` — the carried iter-0/iter-1 lesson applied correctly
— and the `status: "committed"` bug the developer caught themselves (ancestry alone is trivially true
because `freeze_commit` is pinned to the pre-generation `HEAD`) is a genuinely subtle catch, fixed
with a `git cat-file -e` presence check and a regression test that walks a real temp repo through
uncommitted → partially committed → fully committed.

Where the domain work is weaker is at the seams the era's own constitution says are load-bearing:
provenance is asserted rather than mechanically proven (B3), the freeze-set is not portable (B1) and
omits the artifacts it is meant to protect (B7), and the one-epoch rule has no enforcement (B5).
None of these makes the shipped epoch wrong — I checked, and it isn't. They make it **unguarded**,
which is a different and, for an irreversible artifact, more dangerous property. Two of the four are
now closed.

## 5. Recommended Next Step

**Proceed** — J-06 is genuinely done and the epoch is honest, guarded, and operator-visible. But the
next iteration in the Binding Execution Order is J-07, the first real outcome read, and **B1, B2 and
B5 must be resolved before that lock engages**, because §8.5 forbids science-affecting change after
the first read:

1. **B1 (blocking for J-07):** make `generate_freeze_set` emit repo-relative keys and
   `verify_freeze_set_unchanged` resolve them against the repo root (passing absolute keys through
   unchanged, so the hermetic temp-dir fixtures keep working), then regenerate `freeze-set.json` and
   `freeze-record.json`. `epoch_id`/`manifest_hash` are unaffected — `freeze_set_hash` is not in
   `generation_inputs` — so this is not a second epoch, but **it amends a post-barrier frozen
   artifact and needs an explicit owner ruling** before anyone does it. Fold B7 in at the same time
   (add the tracked registry/manifest files and the generation CLI to the enumerated set).
2. **B2 (blocking, cheap):** commit this iteration's science-file changes so every freeze-set path's
   pinned bytes exist in Git history. Until then a `git checkout --` on
   `app/research/foundry_compiler.py` destroys a state §8.1 forbids recreating.
3. **B5 (owner ratification, not code):** the era's history contains a discarded real `epoch_id`.
   The disclosure is complete and the substance is defensible; it needs an explicit owner decision
   that the pre-commit correction was legitimate, and that §8.1's uniqueness will be enforced by
   something more durable than a file's presence, before J-07 spends any evidence.
4. Non-blocking: B6 (record the partition as a ratified interpretation), B8 (stale comment), F1
   (the family/variant rendering branch stays untested until an epoch compiles something).

Do not treat any of the above as license to regenerate the epoch. §8.3 and this spec's own OUT OF
SCOPE are explicit: a flawed-but-honest real epoch is handled at the owner level, never by a second
generation.
