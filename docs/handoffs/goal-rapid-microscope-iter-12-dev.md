## What Was Built

Three gates the iteration-11 independent audit found open, per `docs/rapid-validation-spec.md` r6/r7 (owner rulings 2026-08-18/19), plus two cheap companions and J-07's regression-coverage restoration. All work is confined to `vault.py`/`tick_recorder.py`/`micro_chain_ledger.py`/`main.py`; zero frontend files touched (no UI change this iteration, per spec).

**TR-25 — vault-ledger integrity, fail closed (spec §7.8).** Every normal reader of either vault ledger now goes through a GATED read — new `VaultShardLedger.verified_rows()` / `VaultUniverseLedger.verified_rows()` — which calls `verify_chain()` FIRST and raises a new typed `VaultLedgerCorruptionError` on any failure, never returning a result computed over a tampered or truncated chain. Wired in at the lowest shared choke points (`_latest_rows_by_dataset_id`, `_latest_universes`, `find_universe`), so every public predicate/mutator in the module inherits the gate transitively — including `walkforward.py`'s direct `currently_sealed_dataset_ids` call and `routes.py`'s `get_withheld_dataset_ids` dependency, with **zero changes to either of those files**. A single global FastAPI exception handler in `main.py` (the existing `RealDataError` precedent) maps the new exception to HTTP 503 across every route it can reach, in both `micro_routes.py` and `routes.py` — verified live (see Pre-Handoff Verification below), not just unit-tested.

A full lawful-recovery primitive implements spec §7.8's sequence: `preserve_corrupt_ledger` (byte-for-byte forensic copy of the corrupted ledger + its tail anchor, before any repair), `recover_shard_ledger` (identifies the last verified row, re-derives a caller-supplied trusted-source reconstruction using the exact `HashChainedLedger.append_row` hashing algorithm, and tests whether it reproduces the ledger's own committed tail anchor exactly — a hash-attested proof, never the operator's word). A **proven-complete** reconstruction rewrites the canonical ledger and resumes normal service, reporting the exact prior state. An **unprovable** reconstruction (missing, wrong, or no suffix supplied) refuses to truncate-and-continue: every shard the trusted prefix still names gets a new terminal `STATE_EXPOSURE_UNKNOWN` row — permanently ineligible for sealed-OOS use, enforced for free by the *existing* single-shot lifecycle guards (an `exposure_unknown` shard matches neither `sealed` nor `assigned`, so `assign_shard`/`expose_shard`/`seal_shard` already refuse it). Every recovery attempt — proven or not — is recorded permanently in a new third ledger, `VaultRecoveryLedger`, kept separate from the ledger it's recovering (so a corrupted ledger can never hide the record of its own corruption). Three small additive methods on `HashChainedLedger` (`head_anchor_path`, `read_tail_anchor()`, `rewrite_from_recovery()`) support this — purely additive, the other two consumers of that shared primitive (`ExposureRegistry`, `WalkForwardLedger`) are untouched.

*Disclosed scope decision:* `seal_shard`/`assign_shard`/`expose_shard` gate on their own (shard) ledger's integrity only, not additionally threaded with a required `universe_ledger` parameter. Grounds logged in `vault.py`'s own module docstring: zero production call sites of these three functions exist today (everything that calls them is a test), so widening their signature would force a ~90-call-site mechanical migration across 10 test files for a currently-unreachable risk. TC-2's own literal text ("no sealing, no assignment") is satisfied by gating the shard ledger, the one these transitions actually read/write; a test pins exactly that.

**TR-27 — nonced rule commitment (spec §7.2/7.5, r7).** `register_universe` now mints a high-entropy `commitment_nonce` (`secrets.token_hex(32)`) at registration and computes `rule_commitment = sha256(nonce ‖ canonical_rule)`, served in place of the plain `rule_hash` at every disclosure stage. `rule_hash`/`compute_rule_hash` stay exactly what they were — the ledger's own internal, never-served freeze/idempotency identity function. The reveal gate widened in the **same diff**, per the session's hard-won lesson ("never widen one side of a paired mechanism and leave its twin narrow"): `_fully_exposed_universe_ids` (ledger-tracked-only — the iteration-11 audit's own two-GET subtraction target, `vault._fully_exposed_universe_ids`) is replaced by `_whole_pool_released_universe_ids`, which requires every member of the universe's ORIGINAL registered pool to be released, not merely every member the ledger happens to track.

**A real defect found and fixed before ship.** I dispatched an independent adversarial-review subagent against my own diff (no independent auditor runs this iteration per the pump's carried context, so I substituted one). It found that my first implementation of `_whole_pool_released_universe_ids` keyed its "released" check on `(symbol, session_date)` pairs alone — so a SECOND, different `dataset_id` sealed+assigned under the identical pair as an already-exposed first shard (a re-recorded/retry day, spec §7.7) would satisfy the pair-coverage check while genuinely still withheld, reopening the exact two-GET subtraction class TR-27 exists to close. Fixed in the same diff: the predicate now ALSO requires that no ledger-tracked shard of that universe (any `dataset_id`, any row) is short of `exposed`, in addition to the pair-coverage check. Pinned with a dedicated regression test (`test_two_shards_sharing_one_pair_keep_the_universe_hidden_even_after_one_is_exposed`) and a second test closing a related coverage gap the reviewer flagged (`test_tc5_a_wrong_nonempty_reconstruction_is_also_refused_never_treated_as_proven` — a *wrong but non-empty* recovery suffix, not just an empty one).

**Symbol/date normalization (cheap companion).** The universe-rule membership test inside `unresolved_pool_universe_by_dataset_id` (test (b)) now compares symbols case-insensitively on both the registered rule and the incoming record, so `AAPL` and `aapl` withhold each other's recordings in both directions (TC-12/TC-13). Deliberately scoped to this one predicate — `expected_recording_pairs`/`verify_recording_batch` (TR-4's cherry-pick check) keep their own byte-exact matching, since the iteration spec names only "the universe-rule test."

**TR-28 — coarse pre-release volumes (spec §7.1, r7).** `tick_recorder.py`'s `_progress_view` now ALWAYS serves `trades_total_bucket`/`quotes_total_bucket` (a frozen 9-band order-of-magnitude scheme, e.g. `"1M-10M"`, never a rounded number) in place of the exact `trades_total`/`quotes_total` — never conditionally, no new coupling to `vault.py`. This is the phase spec's own explicitly sanctioned scope-reducing option (NOTES: recording strictly precedes any possible exposure, so this surface can never legitimately need to flip to exact; threading per-universe vault state through the recorder was explicitly out of scope this iteration). The internal running totals (`_publish`) stay exact — only the served projection buckets.

**J-07 regression coverage restored.** Confirmed, by reading `demo_runner.py`'s `normalize_url` source, that a deterministic golden replay script is genuinely infeasible for J-07's surface: the replay runner forcibly rewrites any absolute localhost URL onto the run's single frontend `base_url` host:port with no per-step override, so a script can't express "navigate to the backend's own origin" (J-07 has no frontend page — J-08's unbuilt scope). Restored `runs/goal-session-rapid-microscope/state/golden-gaps` (content: `J-07`) plus a durable in-code explanation in `micro_routes.py`'s `get_graduation` docstring, naming the exact URL and expected body text (`{"families":[],"message":"No candidates ledgered.",...}`) so QA's LLM browser lane can capture a fresh screenshot this iteration (iteration-10's own `UT-J-07` precedent).
