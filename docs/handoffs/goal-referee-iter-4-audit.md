## 2. Findings

### Backend Findings

**B1 — IMPORTANT (gap, open — needs an owner ruling): `min_attainable_p` advertises a p the exact
method can never attain**

`apps/backend/app/research/referee_stats.py:517` serves `"min_attainable_p": 1.0 / (draws_used + 1)`
for **both** branches. This iteration's entire point is that in the enumeration branch the observed
grouping is a guaranteed member of the enumerated space, so `extreme >= 1` and the smallest
producible `p` is `2 / (draws_used + 1)`. The served disclosure therefore understates the floor by
exactly the factor this iteration just fixed in the p itself.

Measured on the module's own attestation fixture (my run of `run_oracle_attestation()` against the
current build): `permutation_p = 0.006644518272425249` (`== 2/301`, i.e. the response sits exactly
*on* the floor) while `min_attainable_p = 0.0033222591362126247` (`== 1/301`, unattainable in this
mode). The same shape is visible in a pre-existing hand-derived test,
`apps/backend/tests/test_referee_stats.py:312`: `p == 0.5` (`== 2/4`, the floor) beside
`min_attainable_p == 0.25`.

Why this matters later, not now: nothing consumes the module today, but `docs/goal.md:511` lists
"min-attainable-p disclosures" as served output, and J-04–J-08 are the first consumers. A
consumer reading this field to answer "can this evaluation even reach the registered target?" gets
`yes` when the honest answer is provably `no` — the exact class of over-promise the era's
"`insufficient_sample` is an answer, never a reason to widen anything" anti-goal exists to prevent.

**Not fixed, deliberately.** `docs/referee-statistical-spec.md:168` says "the minimum attainable p
(granularity) is served beside every p" — two readings that disagree here (granularity/step size =
`1/(draws+1)`, which the code satisfies; minimum attainable value = `2/(draws+1)` in exact mode,
which it does not). Changing it would alter an already-shipped served value and require editing a
pre-existing, hand-derived iter-3 assertion, in an iteration whose scope explicitly forbids
re-deriving this module's shipped constants. This project's own T-1 rule — applied by this very
iteration to drop Lead 2 — says an ambiguous clause is surfaced for an owner ruling, never
improvised. Severity: I was genuinely unsure between IMPORTANT and GAP and chose the higher.
If the owner rules for the "attainable" reading, the whole change is one line —
`"min_attainable_p": (2.0 if use_enumeration else 1.0) / (draws_used + 1)` — plus the two
assertions at `tests/test_referee_stats.py:312` and `:461`. `sign_flip_result`
(`referee_stats.py:570`) is correct as-is: it is always Monte-Carlo, where `1/(b+1)` is genuinely
attainable.

**B2 — GAP (open): the floor guarantee holds for finite inputs only**

With a non-finite observation the guarantee silently breaks: `_t_statistic` returns `NaN`,
`_is_extreme` (`referee_stats.py:266-271`) is `False` for every draw *including the observed
grouping*, and the branch returns a below-floor p. Measured just now on the current build:
`{'s0': ([1.0, nan], [2.0, 3.0])}` → `p = 0.14285714285714285`, `draws_used = 6`, floor
`0.2857142857142857`; `inf` in place of `nan` → `t = inf`, `p = 0.5714285714285714` (meaningless
rather than refused). No input validation exists in the module and none was specified. Nothing
feeds it today; J-04's evidence adapters are the first producers, so either they must reject
non-finite observations or this module must (the spec's `insufficient_sample` state is the natural
home). Documented, not fixed — the spec did not require solving it and a validation path is a new
behavior, not a surgical fix.

**B3 — OBSERVATION (verified clean): the Lead-1 refactor is genuinely value-preserving**

`playbook_occurrence_readiness` changed its loop from `for record in newest_by_date.values()` to
`for session_date in sorted(newest_by_date)` (`referee_evidence.py:271-283`). I traced the three
ways that could have changed a served value and all three are safe: the dict key *is*
`record["session_date"]` by construction (`_newest_per_session_date`, `:229-232`);
`per_setup_side` is built from `sorted(cells.items())` (`:291-294`) so it is independent of visit
order; and `cell["sessions"]` is a `set` whose only use is `len()`. `signals_at_current_basis` is a
plain count. The shared `_is_stale_basis` predicate (`:235-252`) is a faithful de-duplication of
the two former inline checks (`!=` on basis, `!=` on fingerprint, OR-combined), and both call
sites pass their own already-resolved values, so the differing record shapes at the two sites are
handled without assuming a common shape.

**T2 — GAP (open): TC-8's assertion is a wide statistical band, not an equivalence check**

enumeration ground truth within `6 * sqrt(p*(1-p)/b)` ≈ ±0.024 on p. The developer's impossibility

## 3. Domain Assessment

The statistical core is correct on the point that mattered, and for the right reason. The fix does
not merely make the two summation paths "close" — it makes the observed grouping's `T*` **bit-identical**
to `t_obs`, which is the only thing that can make the floor unconditional. I re-derived the chain
rather than trusting the handoff: for the observed joint, `combo = (0..n1-1)` (the first tuple
`itertools.combinations` yields, and `values = group1 + group2` at `referee_stats.py:402`), so
`g1_sum` is `math.fsum(group1)` and `g2_sum` is `math.fsum(group2)` — the exact operands
`_t_statistic:243` uses; `delta_star` is the identical expression on identical operands;
`weights[session] * delta_star` is the identical product `_t_statistic:248` sums; and because
`math.fsum` is exactly rounded (hence order-independent), `math.fsum(terms)` equals
`_t_statistic`'s numerator even though `permutation_test` iterates sessions in sorted order and
`_t_statistic` in insertion order. `total_weight` is the same `math.fsum(weights.values())` on both
sides. Therefore `t_star == t_obs` exactly, `_is_extreme` is `True` under all three sidedness
values, `extreme >= 1`, and `p >= 2/(draws_used + 1)` — for finite inputs (see B2).

Empirical corroboration, my own generator and seeds (7 group shapes including three the shipped
tests never use, 1–5 sessions, all three sidedness values, null and strong-separation regimes):

| Build | null regime (3,515 enum cases) | tail regime (3,520 enum cases) |
|---|---|---|
| shipped (fixed) | **0** violations | **0** violations |
| half-revert (cross-session only) | 1 | 208 |
| reconstructed pre-fix | 17 | 395 |

The developer's "extension beyond the plan's literal text" was therefore not scope creep but a
necessary condition for the DoD's own unconditional claim, and it is confined to the enumeration
branch — the seeded branch's `g2_sum = total - g1_sum` (`referee_stats.py:500`) is byte-unchanged,
correctly, since its `+1` convention never requires the observed grouping to bit-match itself.

The attestation discipline is sound and now genuinely fail-closed: I ran `run_oracle_attestation()`
against the current build and got `stats_core_version='referee-stats-v2'`, `passed=True`,
`actual == _ATTESTATION_EXPECTED`, byte-identical across two calls, `verify_oracle_attestation`
`True` for the record and `False` once only the version string is set back to `"referee-stats-v1"`.
The developer's honest claim that the pinned numbers did not move is **confirmed**, not merely
plausible: I ran a reconstructed pre-fix build's attestation and it produces the identical `actual`
dict. Worth recording as a bonus: the pinned `permutation_p` sits exactly at the new floor
(`2/301`), so the attestation fixture is itself now floor-binding — a reintroduction of the bug on
that fixture would break the pin. `_ATTESTATION_TOLERANCE` (`:660`) is untouched, so no gate
loosened.

Lead 1's disclosure is honest and additive, and Lead 2 was genuinely left alone (`git status`
confirms zero diff to `edge_report.py`; the strategy adapter is untouched). The Lead-2 drop is
documented with a full investigation record rather than a vague TODO, which is the right handling

## 5. Recommended Next Step

Proceed to J-04, with two things carried forward explicitly rather than as folklore:

1. **Rule on B1 before J-04 consumes `permutation_test`'s output.** Either rename/redefine the
   field per the "granularity" reading (and say so in the spec sentence at
   `docs/referee-statistical-spec.md:168`), or make it branch-aware
   (`(2.0 if use_enumeration else 1.0) / (draws_used + 1)`) and update the two hand-derived
   assertions. It is a one-line change either way, and it is much cheaper to settle while the
   module still has no callers.
2. **Have J-04's evidence adapters refuse non-finite observations** (B2), or the floor guarantee
   this iteration paid for silently lapses on the first corrupt record.

Also worth a `lessons.md` entry, because it cost real time this pass and will cost the next agent
the same: `apps/backend/pyproject.toml` sets `addopts = "-q"`, so any agent that runs
`pytest tests/ -q` gets `-qq` and **no final `N passed` summary line at all** — only the exit code
is authoritative. And pytest's `lastfailed` cache retains entries for node IDs that no longer
exist in the tree, so it is not evidence of a failing run; every one of the 21 entries I found
there referred to tests deleted in earlier eras.

Finally, a test-design lesson worth pinning for every later Referee journey: a floor/extremum
property test generated under a pure null is nearly blind, because the floor is essentially never
approached there. Generate in the regime where the property **binds** (strong separation), and
assert that it binds (`at_the_floor >= N`) so the generator cannot drift out of that regime
unnoticed.
